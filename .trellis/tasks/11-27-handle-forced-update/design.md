# 更新拦截设计

## 范围与行为

目标为 `com.bilibili.app.in` 3.20.4。用户确认拦截应用内自动检查、手动检查和强制更新提示；设置项默认开启，用户可关闭。关闭后宿主的原有行为应恢复，不能因为拦截逻辑而继续伪造“已是最新版本”。

目标 APK 的静态分析已在 [调查记录](./research/update-investigation.md)中定位 Gripper 更新入口及自动、手动、强制更新的分支；应在设备上确认其实际调用和回调契约，再按已证实的边界拦截。不要把新版上游的类名、空返回或异常机制当成旧版兼容性的证据；不能确定目标时记录缺失并保持宿主可启动。处理共享响应时只修改经证实属于更新的数据，不拦截整个业务响应或其他错误。

## 结构与数据流

1. 通过已有模块启动和 `RoamingRuntime` 流程，在实际运行目标代码的进程安装适配 hook；仅在已确认的包名及宿主版本适用范围内生效，避免影响其他宿主。
2. 在 `ModuleSettings` 定义持久化布尔键和默认值，由现有设置 UI 与 `ModuleSettingsBridge` 共享。更新拦截优先读取 provider，provider 不可用时读取框架远端偏好，两者均不可用时放行并记录；一旦读到关闭，该 hook 实例在其存续期间保持关闭，正常切换按界面提示重启宿主。设置 UI 按开启/关闭顺序协调本地与远端写入，并在同步未确认时提示；两个存储不能原子提交，故障限制见调查记录。
3. 针对已确认的方法及签名使用现有 libxposed/反射辅助工具；hook 回调按当前设置决定拦截或执行原路径。若启用状态只能在宿主重启后可靠切换，界面应明确提示并在验证中覆盖重启。
4. 以最小可验证的方式处理手动检查反馈，不能宣称成功查询了更新；精确反馈与目标宿主实际调用方式一起验证。对可控的强制更新样例，开启时不阻断操作，关闭时保留原始行为。
5. 使用不含账号、令牌或响应隐私数据的诊断信息区分目标未找到、hook 安装成功和实际命中；现有运行时的工厂数量不是各 hook 安装成功的证明。

## 设置界面

- 在现有“启动净化”区使用 Android Views 的设置行和开关，不引入新页面、配色或组件框架。标题建议“屏蔽应用内更新检查”，说明应涵盖自动、手动检查和强制更新；文案按实际重启行为调整。
- 确保新的开关具有可被无障碍服务读取的名称、明确的开关状态和至少 48 dp 的可操作触摸区域；避免只依靠颜色表达状态，并检查常用字体缩放及窄屏显示。
- 原生设备上核对默认开启、关闭、重新开启、离开页面返回以及重启宿主后的状态。现有布局和 [UI 研究摘要](./research/ui-settings-decisions.md)是参考，具体实现遵循已确认的行为。

## 兼容、验证与回退

- 不修改系统或应用商店的更新机制，不扩大其他宿主版本的支持承诺，不屏蔽登录、内容加载或无关网络请求。
- 先以真实 3.20.4 目标建立自动及手动检查的基线，再使用可控的强制更新样例或已复现响应验证开启、关闭两种状态。若无法构造或复现强制样例，保留该验收未通过状态并明确报告，不以构建成功或弹窗消失代替验证。
- 调试构建与必要的聚焦回归测试之外，设备验收必须记录框架、模块作用域、宿主版本、设置状态、目标命中及行为结果。保持原有偏好值；回退产品变更时不删除用户偏好或设备数据。

## 已知技术未知项

- 3.20.4 的主进程入口、启动与手动调用及可控缓存对象已有设备证据；`FORCE` 动作和热重载未单独触发，真实服务端强制响应与远端偏好同步故障仍有覆盖限制。REA Java 适配器尚未验证 DEX 语义分析；隔离 JADX 回退及其限制见调查记录。
